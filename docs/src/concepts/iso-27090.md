# ISO/IEC 27090

This page covers `ISO_IEC_27090`, a pack of 31 requirements for the guidance in ISO/IEC 27090:2026
on security threats and compromises to AI systems. The standard is guidance and has no certification
scheme. Nothing here is an audit, a certification or a statement that a system is secure. The
standard's text is not reproduced; buy the standard for it.

## What it is

A native pack, with one row per guidance clause that asks for something. Each row has the clause
number, its heading from the standard's table of contents, and one line in this project's own words
on what we look for. Links to other frameworks are the project's own judgement at low confidence.

| Group | Clauses |
|---|---|
| Practices | 5.1 general (its two requirements), 5.2 AI governance programme to 5.7 red teaming |
| Threats | 6.2 data poisoning to 6.11 considerations for AI systems, and Annex B (B.2 denial of service to B.7 model input leak; provisional numbering) |
| Mitigations | 7.2 conflicting interactions of mitigations to 7.9 optimising the size of the model |

The "General" clauses 6.1 and 7.1 and the informative Annexes A and C have no row. The Annex B row
numbers come from a public outline and are not yet checked against the standard's text.

ISO/IEC 27090 is not a harmonised standard, so following it gives no presumption of conformity
under Art. 40 of the EU AI Act. Use it as a structure for the threat register behind Art. 15(5)
and for the security part of the Art. 9 risk work. It covers deliberate attacks on AI systems; the
rest of the EU AI Act (accuracy, data quality and bias, human oversight, instructions for use, the
quality management system) is covered by the `EU_AI_ACT` target.

## Does it apply to you

Two questions in the manifest decide whether the pack applies: whether the organisation builds or
operates an AI system rather than only buying a finished service, and whether a customer contract or
internal policy commits you to it. Without a commitment the outcome is voluntary; an organisation
that builds or operates no AI system reads not applicable. Confirm with your adviser.

Within the pack, three yes/no questions rule out rows that a system cannot face. Answer them under
`framework_inputs.ISO_IEC_27090.scope`; the rows a `false` rules out leave the report by themselves,
each listed under `excluded` with a reason that names the answer, and never fail a gate.

```json
{
  "framework_inputs": {
    "ISO_IEC_27090": {
      "scope": {
        "trains_models": false,
        "uses_retrieval": false,
        "public_api": false
      }
    }
  }
}
```

| Answer `false` to | Rows it takes out |
|---|---|
| `trains_models`: do you train or fine-tune models? | 6.4, 6.6, 7.6, 7.9, B.6; and 6.2 when `uses_retrieval` is `false` too |
| `uses_retrieval`: do you use retrieval over external content? | 6.2, only together with `trains_models` = `false` |
| `public_api`: is the model reachable through a public API? | 6.5, 7.8, B.2 |

### Scoping: rows that may not apply

- A question you leave out is unanswered and takes nothing out. Only `false` does.
- A row you exclude yourself under `excluded` keeps your reason.
- A row you attest stays in the report: the attestation says it applies.
- Everything else stays in. A hosted model you only call still brings the general requirements
  (5.1), supply chain (5.5, B.3), prompt injection (6.9), the system considerations (6.11) and
  input leakage (B.7). Exclude any other row that does not apply by hand, with your reason.

## How rows are decided

Every row takes a provider attestation. It reads `Unverified` until you record one under
`framework_inputs.ISO_IEC_27090.attested`, and `Met`, labelled `attested`, once you do.

```json
{
  "framework_inputs": {
    "ISO_IEC_27090": {
      "attested": {
        "ISO_IEC_27090:5.5": {
          "statement": "Third-party models and datasets are pinned by hash and reviewed before use.",
          "attested_by": "Jane Doe",
          "attested_at": "2026-11-02"
        }
      }
    }
  }
}
```

25 of 31 requirements are checked from evidence as well: a supporting probe finds a file or code
convention, or an output evaluator tests the same thing. 6 of 31 are attestation only. The target is
20 of 31; the pack is above it. A scaffold left unfilled does not count as evidence. A row reads Met,
Partial, Missing or Unverified.

| Evidence class | Rows |
|---|---|
| Machine | 3 |
| Hybrid | 22 |
| Organisational | 6 |

- An evaluator only counts when you supply an eval (`--sample-set`). A row takes the worst status of
  its sources, so a failing evaluator makes an attested row `Missing`, and a passing one leaves it
  `Met`. Rows 5.7, 6.8 and 6.9 have an evaluator of their own (`EVAL_ADVERSARIAL_V1` or
  `EVAL_DATA_LEAKAGE_V1`); 6.3, 6.4, 6.6 and B.6 take one as corroboration.
- A supporting probe only points at evidence and only reads the repository under `--repo-root`. It
  never makes a row `Met` by itself and never lowers one. An unattested row with a probe hit reads
  `Unverified`, with the file named in the rationale. By default an `Unverified` row never fails a
  gate; with `fail_on: unverified` it fails for want of an attestation, whatever a probe found.
- What a probe finds is a file name or an import, not proof that the control works. A probe matches
  names, so a renamed file is not found. Row 6.10 has no output evaluator: the lexical safety
  evaluator only reads what the model says.

| Probe | What it looks for |
|---|---|
| `ai_supply_chain_pins` | An SBOM with its format header; a hash pin in `dvc.lock`, a `*.dvc` file or a model or dataset lock file; or Python that pins a hub model to a commit hash. A revision of `main` or a tag is not a pin. |
| `ai_threat_model` | A threat model file or folder whose text names an AI-specific attack and holds more than headings. |
| `ai_red_team_report` | A red-team file or folder that names an AI-specific attack and a result. |
| `rate_limiting_config` | A rate-limit library imported in code, Django REST framework throttle rates, an nginx `limit_req` or `limit_conn` directive, or an Envoy rate-limit filter. A name in a README or a dependency list does not count. |
| `event_log_evidence` | The oversight log or agent decision log inside the repository. |

### In the technical documentation

Annex IV point 2(h) of the EU AI Act asks for the cybersecurity measures put in place, and Art. 15(5)
names the AI-specific vulnerabilities they address. When `ISO_IEC_27090` is among the manifest's
`compliance_targets`, [`docs generate`](../cli/docs-generate.md#cybersecurity-section) adds a
`cybersecurity` part to the dossier, copied from the same report `check` and `gaps` produce:

- one entry per row: clause id, heading, status, source (`attestation` or `evaluator`) and evidence
  reference;
- counts per status (Met, Partial, Missing, Unverified);
- the rows the manifest excluded, listed apart with the reason given;
- a fixed lead-in: the part is structured using ISO/IEC 27090 guidance, it is not a certification and
  it gives no presumption of conformity.

`--render md` and `--render pdf` print the same part. Without the target the key is absent, and the
dossier, its checksum and its signature are what they were before. The part reports statuses; it adds
no checks and does not affect `annex_iv_complete` or the exit code. See the
[coverage ledger](annex-iv-coverage.md).

## Scaffolds

Two starting documents are written into the repository on request: an AI threat model
(`docs/threat-model.md`) and a red-team report (`docs/red-team-report.md`). Each has `_fill in_`
placeholders, and left unfilled they do not count as evidence. Three templates help with a threat and
its mitigation, an evaluation record and a security configuration. They are drafts, not legal advice.

## Gate in CI

```sh
opencomplai check --target ISO_IEC_27090 --gate ISO_IEC_27090 --gate-fail-on missing --repo-root .
```

The command exits 1 and lists the requirement ids when a row at the chosen level is found. By
default an `Unverified` row never fails the gate. See
[Gating other frameworks](../cli/check.md#gating-other-frameworks). `gaps --target ISO_IEC_27090`
prints the table, and `controls` and `recommend` carry its requirements.

## What stays attested and why

Six rows have no evidence a tool can read, and only a person can vouch for them:

- 5.1, general: that controls are chosen from a risk assessment, a judgement only the accountable owner can vouch for.
- 6.11, considerations for AI systems: that the organisation weighed the AI-specific threat across the life cycle.
- 7.2, conflicting interactions of mitigations: that the security practice is applied day to day.
- 7.3, continuity of mitigations across the AI life cycle: that the security practice is applied day to day.
- 7.9, optimising the size of the model: that the response is decided and followed, not just written down.
- B.7, model input leak (provisional numbering): that the organisation weighed the topic and acted on it.

## Review status

Every row is flagged `mapping not yet reviewed`. No flag has been cleared. The links to EU AI Act
articles, NIST AI RMF subcategories, ISO/IEC 42001 rows, ISO/IEC 27001:2022 Annex A controls and SOC 2
criteria are this project's mapping at low confidence; no public crosswalk for ISO/IEC 27090 existed
when it was written. A few follow references the standard makes itself (clause 5.1 points threat
considerations to ISO/IEC 42001 A.6.2.3 and A.6.2.6). See [Framework mappings](../frameworks/mappings.md).
Clause numbers and headings of clauses 5 to 7 were checked against the published table of contents.
